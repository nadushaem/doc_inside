# DocRadar: агрегатор врачей с аспектным анализом отзывов

Пет-проект на стыке NLP и healthtech. Собирает отзывы о врачах с публичных
агрегаторов (`prodoctorov.ru`, `napopravku.ru`) по нескольким специальностям, склеивает профили одного и того же врача с разных сайтов в единую
персону и извлекает из текста отзывов конкретные аспекты (компетентность, время ожидания, вежливость персонала, готовность прийти
повторно), после чего ранжирует врачей под приоритеты конкретного пользователя вместо
усредненной оценки по звездам.

Текущий статус: готовы сбор отзывов и дедупликация врачей между источниками.
Аспектная разметка, скоринг и сайт — впереди (см. Roadmap).

## Как это устроено

В корне репозитория лежат:

- `main.py` — оркестрация сбора: обход всех источников × специальностей ×
  городов, ведение индекса врачей и инкрементальный докачивание отзывов;
- `dedupe.py` — поиск дублей врачей между источниками: скоринг пар, кластеры,
  очередь на ручную проверку;
- `merge.py` — склейка подтвержденных кластеров в единые «персоны»;
- `storage.py` — чтение/запись json и слияние отзывов без дублей;
- `ids.py` — стабильный идентификатор отзыва;
- `config.py` — города, специальности и лимит врачей на специальность для
  тестовых прогонов;
- `requirements.txt` — зависимости проекта.

Логика сбора разложена по папке `sources/`, обработка собранного — по скриптам
в корне (`dedupe.py`, `merge.py`).

### Источники (`sources/`)

- `base.py` — `DoctorRef` (ссылка на врача внутри источника) и протокол
  `Source`, который обязан реализовать каждый источник: `list_doctors()` и
  `fetch_new_reviews()`.
- `browser.py` — общий `goto_with_retry()`: переоткрывает страницу при таймауте
  Playwright.
- `prodoctorov/` — каталог с постраничной пагинацией (`?page=N`), отзывы на
  отдельных страницах (`/otzivi/N/`), тональность берётся из css-классов
  карточки (`positive` / `negative`).
- `napopravku/` — каталог вида `page-N/`, отзывы подгружаются кнопкой «Показать
  ещё» (перед сбором включается сортировка «по дате»), рейтинг считается по
  количеству активных звёзд.

Внутри каждого источника одинаковая раскладка:

- `config.py` — домен, user-agent, таймауты, задержки между страницами,
  предохранители по числу страниц/кликов, словари слагов;
- `browser.py` — контекстный менеджер с готовой Playwright-страницей;
- `catalog.py` — сбор списка врачей специальности в городе;
- `fetcher.py` — обход страниц отзывов конкретного врача;
- `parser.py` — разбор html: отзывы и блок профиля (ФИО, вуз, год выпуска);
- `adapter.py` — тонкая обертка, реализующая протокол `Source`.

Каждый источник отдает отзывы одинаковыми словарями (`text`, `source`,
`doctor_url`, `date_raw`, `date_iso`, `rating`, `site_sentiment`) и профиль
врача (`full_name`, `university`, `graduation_year`, `degree_speciality`),
чтобы дальше по пайплайну было не важно, откуда пришли данные.

### Сбор и инкрементальность (`main.py`)

1. Для каждой пары «специальность + город» источник отдаёт список врачей.
   Каждый врач попадает в общий индекс под ключом `{источник}:{id_на_сайте}`;
   если врач нашёлся сразу в нескольких специальностях, они накапливаются в
   поле `specialities`.
2. Для каждого врача поднимаются уже сохранённые отзывы, из них считаются
   известные id (`ids.py`: sha256 от `doctor_url`, даты и первых 50 символов
   текста — 16 hex-символов).
3. Источник обходит страницы отзывов и останавливается, как только встречает
   уже известные id: при регулярных прогонах качаются только новые отзывы.
4. Новые отзывы дописываются в файл врача, профиль (ФИО, вуз, год выпуска)
   обновляет запись в индексе.

Сбой на отдельном враче или на целой паре «специальность + город» не роняет
прогон: исключение логируется, индекс сохраняется, обработка продолжается.
`DOCTORS_PER_SPECIALITY_LIMIT` в `config.py` ограничивает число врачей для
быстрых тестовых запусков.

### Дедупликация врачей (`dedupe.py`)

Один и тот же врач заведён на разных сайтах по-разному: сменившаяся фамилия,
девичья в скобках, опечатки, отсутствующее отчество, «Наталья»/«Наталия». Скрипт ищет такие пары и раскладывает их по корзинам.

- **Разбор ФИО** — нижний регистр, замена латинских гомоглифов, `ё`/`е`,
  выделение фамилии/имени/отчества (включая тюркские «кызы», «оглы»), корень
  отчества, девичья фамилия из скобок, транслит фамилии и фамилия из slug
  профиля (если она непохожа на текущую — вероятно, прежняя).
- **Разбор образования** — `UNI_RULES` сводят названия к
  идентификатору вуза (`usmu`, `sibgmu`, `sechenov`, …), отдельно вытаскивается
  год выпуска и уровень (вуз или колледж); описания курсов повышения
  квалификации помечаются как ненадежные.
- **Блокировка** — пары-кандидаты берутся только внутри общих ключей (город +
  полное ФИО, город + фамилия и имя, город + имя и корень отчества и т.д.),
  чтобы не сравнивать всех со всеми.
- **Классификация и скоринг** — `classify()` определяет тип совпадения
  (полное ФИО, двойная фамилия, девичья в скобках, опечатка, смена фамилии …)
  и базовый балл, `score_pair()` добавляет за совпавший год выпуска (+2) и вуз
  (+1.5), штрафует за разные вузы, вуз против колледжа, отсутствие общей
  специальности и наличие полных тезок; расхождение годов выпуска больше чем на
  один — вето.
- **Ручная проверка** — выше `AUTO_THRESHOLD_EXACT` / `AUTO_THRESHOLD_FUZZY` пара
  уходит в `auto`, выше `REVIEW_THRESHOLD` — в `pending` (печатается в консоль
  для ручной проверки), ниже — отбрасывается. Ручные решения вписываются в
  `manual_decisions.json` в виде `{"pair_id": true/false}` и на следующем
  прогоне имеют приоритет над автоматикой.
- **Кластеры** — подтвержденные пары объединяются через DSU; кластер помечается
  `needs_review`, если в него транзитивно затянуло отклоненную вручную пару или
  два профиля одного источника без явного подтверждения.

### Склейка персон (`merge.py`)

Кластеры превращаются в записи `merged.json`: `person_id` — детерминированный
хэш от отсортированных ключей кластера, ФИО и образование берутся из самой
заполненной записи, специальности объединяются, ссылки на профили всех
источников складываются в `sources`.

## Как запустить

1. Установить зависимости:

   ```
   pip install -r requirements.txt
   playwright install chromium
   ```

2. Собрать врачей и отзывы:

   ```
   python main.py
   ```

3. Найти дубли врачей между источниками:

   ```
   python dedupe.py
   ```

   Пары с неуверенным баллом печатаются в консоль. Решения по ним вписываются
   в `data/processed/doctors/manual_decisions.json`, после чего `dedupe.py`
   запускается повторно.

4. Склеить подтвержденные кластеры в персоны:

   ```
   python merge.py
   ```

## Данные

Все собранные файлы лежат в `data/` (создается автоматически, в git не
коммитится):

- `processed/reviews/<источник>/<id_врача>.json` — отзывы врача, дописываются
  инкрементально;
- `processed/doctors/index.json` — индекс врачей по ключу
  `{источник}:{id_на_сайте}`: ссылка на профиль, ФИО, город, специальности,
  вуз и год выпуска;
- `processed/doctors/matches.json` — результат дедупликации: корзины `auto`,
  `manual_confirmed`, `manual_rejected`, `pending` и собранные кластеры;
- `processed/doctors/manual_decisions.json` — ручные решения по спорным парам
  (единственный файл, который заполняется руками);
- `processed/doctors/merged.json` — итоговые персоны со ссылками на все
  источники.

## Roadmap

- Разметка и извлечение аспектов из отзывов (ruBERT / rubert-tiny либо
  zero-shot через LLM API), сентимент по каждому аспекту;
- Скоринг и ранжирование врачей по весам аспектов из анкеты пользователя;
- Переезд хранения с json на PostgreSQL (SQLAlchemy) + FastAPI;
- MVP сайта на Streamlit: поиск по специальности и городу, карточка врача с
  разбивкой по аспектам, персональные фильтры;
- Новые источники (docdoc и др.) и новые города — каталог и фетчер под общий
  протокол `Source`;
- Регулярное обновление данных на сервере (cron / Airflow, systemd);
- Логирование вместо `print`, тесты на парсеры и дедупликацию, ruff и
  pre-commit hook.
